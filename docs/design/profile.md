# 详细个人信息页

目标：把「我的」上部的资料卡变成一扇门，通向一个独立的「详细个人信息」页；页内既能看，
也能改手机号、密码、头像、性别、民族、政治面貌、标签。

官方现在是两个页面：「我的信息」`#/myInfor` 与「设置」`#/settings`，另有
`#/changePassword`、`#/myTags` 两个子页面。我们合并成一个页面，减少来回跳。

## 页面结构（设计稿）

```
详细个人信息
├─ 头部：头像（可点改） / 姓名 / 学号
├─ 资料：性别 · 民族 · 政治面貌        → 点任意一项进入修改
├─ 组织：院系 / 专业 / 班级
├─ 标签：阅读 学习 音乐 …              → 点进标签页
├─ 账号安全
│   ├─ 手机号 195****6281  → 更换（短信验证码）
│   └─ 登录密码            → 修改
└─ 说明：姓名、学号、院系、专业、班级由学校维护，应用内不可改
```

「我的」页的资料卡（头像 + 姓名 + 学号 + 年级班级）整体可点，进入这个页面。

## 接口（2026-10-23 只读实测 + H5 源码核对）

读：

| 用途 | 接口 | 备注 |
| --- | --- | --- |
| 详细资料 | `GET student/user/my/info/mine` | 比 `my-info` 多 `mobile`、`ethnic`、`ethnicId`、`politics`、`politicsName`、`personTag`（如 `8,9,5`） |
| 民族列表 | `GET student/get/nation_list` | 数组，按顺序取 `name`；提交用的是 `下标 + 1`（即 `ethnicId`） |
| 标签字典 | `GET dict/user/tag` | `[{id, name}]` |
| 手机号验证码 | `POST common/captcha/mobile` | `{countryCode:"86", mobile:<当前手机号>, type:2}`，验证码发到**旧号** |

写（都是单一动作，必须二次确认）：

| 动作 | 接口 | 参数 |
| --- | --- | --- |
| 改性别 | `POST student/user/update-info` | `{gender: 1 男 / 2 女}` |
| 改政治面貌 | `POST student/user/update-info` | `{politics: 0 群众 / 1 共青团员 / 2 中共党员 / 3 其他党派 / 4 中共预备党员}` |
| 改民族 | `POST student/user/update-info` | `{ethnicId: <nation_list 下标+1>}`（H5 源码推断，待实测） |
| 改头像 | `POST student/user/update-info` | `{avatar: <OSS 直传后的 URL>}` |
| 换手机号 | `POST student/user/update-mobile` | `{oldMobile, countryCode:86, code, newMobile}` |
| 改密码 | `POST student/user/update-pwd` | `{oldPwd, newPwd, newPwdRepeat}` |
| 改标签 | `POST student/user/update-person-tag` | `{personTag: "8,9,5"}`（逗号分隔的 id） |
| 改证件照 | `POST student/photo/update` | `{cardPhoto: <URL>}`，属于成绩单，不在本项目范围 |

要点：

- **改密码成功会让当前 token 失效**。官方直接清 `TOKEN`、回到登录页；我们也必须清本地会话
  并回登录页，否则后续请求全是 `10001`。
- **换手机号的验证码发到旧号**，新号只作为提交值；没有新号验证这一步。
- 密码强度：≥8 位，且同时含大写字母、小写字母、数字、特殊符号（官方前端正则）。
- **头像上传走阿里云 OSS 直传**。已挖到：先 `GET common/aliyun/sts/assume-role` 拿 STS
  临时凭证，桶 `gytx-2ketang`、地域 `oss-cn-hangzhou`，再上传并把返回的 URL 交给
  `update-info {avatar}`。H5 用的是 `aliyun-oss-sdk`；我们没引这个 SDK，需要自己签 PutObject
  （OSS 的 V4 签名）。这一步单独一期，且必须真机验证——签错只是上传失败，不会改坏数据。
- 性别 / 民族 / 政治面貌都是**逐字段**调用同一个 `update-info`，不是整表单提交。

## 分阶段计划

每阶段一个独立提交、独立版本号；手机不在身边时，只用「编译通过 + 单元测试 + 只读接口核对」
验收，并在提交信息里写明「未真机验证」。

| # | 内容 | 版本 | 真机需要 |
| --- | --- | --- | --- |
| 0 | 接口摸底与本文档（当前） | 0.8.2 | 否 |
| 1 | 详细个人信息页（只读）+ 资料卡入口 | 0.8.3 | 是（走查） |
| 2 | 账号安全：修改密码（成功后清会话回登录） | 0.8.4 | 是 |
| 3 | 更换手机号（验证码倒计时、旧号收码） | 0.8.5 | 是 |
| 4 | 性别 / 民族 / 政治面貌（逐字段提交） | 0.8.6 | 是 |
| 5 | 标签页（字典 + 多选保存） | 0.8.7 | 是 |
| 6 | 修改头像（OSS 直传，含格式与大小限制） | 0.8.8 | 是 |
| 7 | 「我的」页收纳与回归，决定是否发版 | 0.9.0 | 是 |

顺序理由：先只读（没有副作用、最容易验证），再改密码（不依赖第三方），再手机号（依赖短信），
再逐字段资料，最后才是标签与头像（要做选择与上传，UI 与网络都更重）。

## 红线

1. 写操作只能在用户点确认之后发，绝不自动重试。
2. 请求参数与响应原文写入 `[action]` 日志（不含密码、验证码、token）。
3. 密码、验证码一律不落盘。
4. 拿不到真机就不宣称「已验证」，只写「编译通过，未走查」。
